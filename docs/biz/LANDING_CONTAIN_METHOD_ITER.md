## 1. 直接落地场景（不是故事，是可开的工单）

### 1.1 场景清单（每个都有：触发 → 动作 → KPI → 钱路径）

| # | 场景 | 方法触发 | 业务动作 | 主 KPI | 钱怎么来 |
|---|------|----------|----------|--------|----------|
| S1 | **客服幻觉制度跳变** | OnlineRFPerm concept fire（ratio≈11.7） | `model_rollback` / `audit_topk` / `retrieval_refresh` | 少工单 / 少退款 / **多承接** | 费率差 × 单价 |
| S2 | **检索支持缺口** | fire + Top-k `rag_hit` 低 | 只开 `retrieval_refresh` | 同上，但归因到检索臂 | 同左；**不**整模回滚 |
| S3 | **生成制度 hop** | fire + rag_hit 尚可 | `model_rollback` + √PO 门控 | 同上 | 回滚成本进回本分母 |
| S4 | **审计止血** | `po_risk0` Top-k | `audit_topk` | 确认差例 + 少坏会话外溢 | 审计件¥进净贡献；回本最快 |
| S5 | **文风/画风漂移** | `style_domain_auc` 高 | 素材/decoding 工单 | CTR / 品牌（**不进客服账**） | 另账；禁止混账 |
| S6 | **对齐合并门禁** | RFPerm-as-Judge fire | 拒合并 / 限量 / Top-k 复核 | 发布放行率 | 避免坏偏好进生产（防损） |
| S7 | **流量外推** | 同费率 × 日会话 | 试点→生产扩量 | 月毛¥ | `prod_mid` 日1万 ≈ ¥3.57M |

**落地的硬规则：** 没有对照臂（acted vs ignored）就不宣称 S1–S4 的增量¥；S5 永不写入客服主账。

### 1.2 本原型主场景（S1）一页纸

```text
平静期 quiet          跳变期 fire+ignored         跳变期 fire+acted
工单率 1.50%    →     15.86%                 →    1.14%
退款率 0.61%    →     10.50%                 →    1.21%
承接率 97.89%   →     75.21%                 →    97.79%
                              ↑恶化（不动作）         ↑拉回（动作）
```

产出（acted 7 日 vs ignored 基准）：

| KPI | 量 | ¥（单价） | 占毛 |
|-----|-----|-----------|------|
| 少工单 | 206 | ¥5,150（×¥25） | 31% |
| 少退款 | 130 | ¥10,400（×¥80） | **62%** |
| **多承接** | **316** | **¥1,106（×¥3.5）** | 7% |
| 毛合计 | — | **¥16,656** | 100% |
| 扣审计净 | — | **¥16,590** | — |

对外一句（可粘贴）：

> 幻觉制度跳变后，客服助手相对同条件不动作：少 206 工单、130 退款、**多承接 316 次**；净贡献 ¥16,590；优先动作 `model_rollback`。

### 1.3 为什么这些场景「直接」

| 要求 | 本设计怎么满足 |
|------|----------------|
| 业务听得懂 | 只讲工单/退款/承接，不讲 AUROC |
| 工程开得出工单 | 三个动作类型已进 seed / SQL / 回本表 |
| 财务收得下 | 周归因 gap=0；单价可 ±20% 扫带 |
| 方法有证据链 | HF hop JSON → `hf_hop_knobs.json` → seed 费率 |

## 2. 多承接逻辑（为什么关键、怎么定义、怎么进账）

### 2.1 业务含义

**机器人成功承接** = 一次会话 **没有** 升级成人工工单，也 **没有** 走到退款。  
在 SQL 里（`vw_cs_assist_daily`）：

```sql
n_contained = SUM(
  CASE WHEN cs_ticketed = 0 AND refunded = 0 THEN 1 ELSE 0 END
)
containment_rate = n_contained / n_sessions
```

这不是「聊完了就算成功」，而是 **质量闭环成功**：用户被助手独立消化掉。

### 2.2 增量「多承接」怎么算（对照，不是绝对值）

\[
\Delta C = \bigl(r^{\text{acted}}_{\text{contain}} - r^{\text{ignored}}_{\text{contain}}\bigr) \times N_{\text{acted}}
\]

本原型：

| 臂 | 承接率 |
|----|--------|
| quiet | 97.89% |
| fire+ignored | **75.21%**（崩溃） |
| fire+acted | **97.79%**（拉回） |
| 提升 | **+22.57 pp** |
| 多承接次数 | **316** |
| 承接单价 | ¥3.5 / 次 |
| 承接贡献¥ | **¥1,106** |

### 2.3 为什么多承接必须单独成项（不能并进「少工单」）

| 点 | 说明 |
|----|------|
| **定义正交** | 少工单只盯 ticket 边际；承接要求 **同时** 无工单且无退款。有人无工单但仍退款 → 不算承接。 |
| **单价不同** | 工单¥25、退款¥80、承接¥3.5——合并会糊掉单位经济敏感度。 |
| **叙事不同** | 少工单/退款 = **止损**；多承接 = **产能/自助率**（机器人真正顶住量）。 |
| **方法映射不同** | 幻觉率下降 → 同时压 ticket/refund **并** 抬 contain；RAG 刷新往往先抬 contain（答得住），再降退款。 |

**关键读法：** 跳变后若不动作，承接率从 ~98% 掉到 ~75%——这是「助手大面积转人工/失败」的运营事故；动作把承接拉回 quiet 水平，**多承接 316 次** 就是事故被按住的次数代理。

### 2.4 多承接 vs 少工单/少退款：会不会双重计数？

毛增量公式三项是 **费率差 × 会话 × 各单价**，不是把同一会话的三种结果加三次：

```text
毛¥ = Δticket×p_T + Δrefund×p_R + Δcontain×p_C
```

- \(\Delta ticket\)：工单率差（ignored−acted）  
- \(\Delta refund\)：退款率差  
- \(\Delta contain\)：承接率差（acted−ignored）  

同一会话在事实表里互斥计入 ticket / refund / contained，但 **增量** 用的是 **臂级费率差**，允许三项同时为正（acted 全面好于 ignored）。  
这是对照会计，不是把一条会话卖三次。单位经济扫单价时三项独立缩放，便于财务改口径。

### 2.5 多承接与方法论的衔接

| 方法信号 | 对承接的含义 |
|----------|--------------|
| OnlineRFPerm fire | 打开窗：只在火情期比 acted/ignored 承接率 |
| 幻觉率 quiet→fire 0.07→0.82 | 解释 ignored 承接崩溃的机制（答错→转人工/退款） |
| 动作落地后幻觉压回 | 承接率回到 ~98% |
| rag_hit 低 | 优先刷检索——往往 **先** 恢复「答得住」= 承接 |
| po_risk0 Top-k | 审高风险会话，减少「漏网」坏答案继续污染承接 |

**异同一句：** 方法层没有「承接」字段；业务层把「制度 hop 被按住」翻译成 **承接率 lift pp**——这是方法→运营最直观的一根针。

### 2.6 多承接在回本 / 周归因里的位置

- **周归因**：每日 `extra_contained_day` 进 \(G_t\)，再按周加总（与工单/退款并列）。  
- **回本**：承接¥进毛贡献 \(G_a\) 分子；不单独拆臂时已含在日均毛¥里。  
- **单位经济**：承接单价 ±20% 时，316 次 × ¥2.8–¥4.2 → 承接贡献带约 ¥885–¥1,327（量固定）。

## 3. 方法论层面的异同（具体 elaborations）

### 3.1 相同（same）— 为什么能叠乘

| # | 相同点 | 落到本原型 |
|---|--------|------------|
| 1 | **都对「制度/画像变了没」敏感** | fire=1 同时打开方法诊断与业务对照窗 |
| 2 | **都要对照，不看绝对值** | quiet / ignored / acted 三臂；方法侧 quiet vs fire batch |
| 3 | **都要轴拆分再动作** | RAG vs generation；文风 vs 偏好；业务三动作臂 |
| 4 | **都有关断条件** | 方法 quiet→退火；业务回本不达标→降级臂 |

没有这些「同」，方法信号无法合法驱动业务账。

### 3.2 不同（different）— 为什么不能混账

| 维 | 方法论 | 业务情景 | 单位经济 |
|----|--------|----------|----------|
| 输出 | fired / ratio / AUROC / P@10 / style_auc | 少工单/退款/**多承接**/动作净¥ | 同量下的 ¥ 带 |
| 时间 | batch / cut 时钟 | 经营日 / **周归因** | 假设扫描（无时钟） |
| 因果声称 | 检测与排序，非因果 | 对照代理，非 RCT | 财务假设 |
| 失败模式 | 漏检/误火 | 对照臂脏、臂定义漂 | 单价拍脑袋 |
| 成功标准 | 火得准、排得准 | 量真实、**gap≈0** | 带内仍净值 |

### 3.3 Relevance 链（异同怎么变成决策）

```text
同：火了 → 打开同一对照窗
异：方法给「火/审谁/动哪轴」；情景给「量」；单位经济给「钱带」
relevance：三层叠乘；缺方法则无窗；缺情景则无量；缺单位经济则财务不收
```

| 问题 | 该层 | 本原型 |
|------|------|--------|
| 跳了吗？ | 方法 | fire，ratio≈11.7 |
| 多接住了多少？ | 情景 · 承接 | +22.57 pp · 316 次 |
| 承接值多少钱？ | 单位经济 | ¥1,106；单价敏感可重算 |
| 这周承接贡献进哪周？ | 周归因 | 进 W1/W2 的 \(G_W\) |
| 为承接付的动作成本几天回？ | 回本 | 三臂均 same_day |

### 3.4 文风轴 vs 客服承接（易错点）

| | 文风/HH | 客服/HaluEval |
|--|---------|----------------|
| 主信号 | style_auc / judge_err | fire / 幻觉率 / rag_hit |
| 承接？ | **无**客服承接定义 | **有** contain 费率 |
| 钱路径 | CTR/品牌 | 工单/退款/**承接** |
| 若混淆 | 误伤偏好头；虚增客服¥ | — |

**异同的产品结论：** 方法论「同构」（都是制度检测），业务「异构」（承接只属于客服面）。

## 4. 迭代更新逻辑（为什么这套能持续转）

### 4.1 迭代环（每一圈都留下可对账增量）

```text
① 方法探针迭代     OnlineRFPerm gate / 特征 / 标签源
        ↓ 产出 fire 时钟 + knobs JSON
② 落地场景迭代     动作路由、臂定义、seed 与真实日志对齐
        ↓ 产出 acted/ignored 费率
③ 量账迭代         少工单/退款/【多承接】公式锁死（pytest）
        ↓ 产出量
④ 钱账迭代         单价、审计成本、动作日成本
        ↓ 产出毛/净¥
⑤ 周归因迭代       日→周加总，锁 attribution_gap≈0
        ↓ 产出可签字周报
⑥ 回本迭代         payback_days / 净ROI / 降级规则
        ↓ 产出仓位（开哪臂）
⑦ 敏感度迭代       hop 强弱带 × 单价±20% × 流量档
        ↓ 产出「还站不站得住」
⑧ 文档/对外句迭代 贡献账 + 对照原型 + Roadmap
        ↓
   下一圈：ignored 留白¥、回本×单价联合、真实 serving 时钟 …
```

### 4.2 本分支已经转过的圈（证据）

| 圈 | 交付 | 锁什么 |
|----|------|--------|
| 方法 | HF landing protos | fire / style_auc / rag |
| 场景 | CS SQL 04–06 | 三臂费率 + 动作拆分 |
| 量+净 | 05 net + pytest | 毛−审计=净 |
| 周+回本 | 07 | gap=0；same_day |
| 单价带 | 08 | ±13,259–¥19,921 |
| 异同图 | method_biz prototype | same/diff/relevance |
| Roadmap | METHOD_LANDING_ROADMAP | 推理/对齐路径 |

### 4.3 迭代原则（写死，防退化）

1. **每圈必须有新的可对账物**（视图 / JSON / 文档数字），禁止只改形容词。  
2. **公式变更先改 pytest**（增量、净≤毛、gap、回本桶、承接定义）。  
3. **承接与工单/退款分列**，迭代时不得合并成一个「质量分」。  
4. **方法迭代不自动改¥**；只改 knobs→seed→重跑账。  
5. **对外句只引用 exec_summary / 周归因 / 回本**，不引用 AUROC。

### 4.4 下一圈建议（承接相关优先）

| 优先级 | 迭代 | 为什么 |
|--------|------|--------|
| P0 | ignored 日「若当时动作」的承接留白次数/¥ | 推动提高 acted 覆盖 |
| P0 | 承接单价单独 ±20%/±50% 情景 | 财务常改自助会话价值 |
| P1 | 按动作臂拆 `extra_contained` | 看刷检索是否更利承接 |
| P1 | 回本分子显示承接分项 | 讲清「回本里有多少来自自助率」 |
| P2 | 真实日志替换 seed 承接定义 | 与工单系统字段对齐 |
