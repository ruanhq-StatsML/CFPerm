# 大模型落地 Use-case 总览（只谈业务）

> **定位**：这些都是把「线上有没有漂 / 该不该动」接到业务动作与对账上的 **use-case**，  
> **不是**大模型训练、对齐算法本身的方法论创新。  
> 方法名只作路由标签：推理流 → **OnlineRFPerm**；数据对齐 / 合并门禁 → **RFPerm**；实例谁先审 → **BOCPD**（PO-risk）。

## 1. 推理：OnlineRFPerm（在线）

**业务故事**：客服 / 助手每天在答用户。某一天起，答非所问、胡编、转人工暴增——这是 **推理质量制度跳变**，不是单条 badcase。

**你要回答的只是：**

1. 哪一段日子算「出事了」（对照窗打开）  
2. 出事之后，若当时动作了 vs 没动作，工单 / 退款 / 自助承接差多少  
3. 接下来开哪张工单：回滚模型、刷检索、还是加审计队列  

**不回答的：** 模型怎么训、对齐 loss 怎么改、有没有新 SOTA。

本仓库原型主数据：HaluEval 式「幻觉标签流」→ 连续时间 `{问题, 回答, 表征, 分}` → 在线火情时间戳。

---

## 2. 数据对齐：RFPerm（批式门禁）

**业务故事**：RLHF / DPO 要合一批新偏好数据，或换一版裁判。合进去之前问一句——**这批数据的偏好映射，还跟黄金集是不是同一套？**

**你要回答的只是：**

1. 合并前：候选批 vs 黄金批，偏好是否「换制度了」  
2. 若换了：拒合并 / 限量灰度 / 强制人工抽检 Top-k  
3. 文风变了 ≠ 偏好变了：文风工单走素材，偏好工单走对齐数据，**两本账**

**跟推理的差别（业务上）：**

| | 推理（OnlineRFPerm） | 对齐（RFPerm） |
|--|----------------------|----------------|
| 时间形态 | 线上连续流，按窗/按日 | 合并前的批次对照 |
| 触发后果 | 运营动作（回滚/检索/审计） | 发布门禁（合 / 不合） |
| 钱路径 | 少工单 · 少退款 · 多承接 | 主要是 **防损**（坏偏好进生产） |

本仓库原型对照面：HH-RLHF 偏好流；**不要**把对齐门禁的信号写进客服主账。

## 3. 还有哪些大模型落地 case（业务 elaborations）

### 3.1 U3 — 客服助手增量账（主落地，见第 4 节）

推理火情打开对照窗之后，把「动作落地」和「同条件不动作」做成经营账：少多少工单、少多少退款、多承接多少次、净贡献多少 ¥、哪一周贡献、哪个动作几天回本。

### 3.2 U4 — 检索缺口 vs 生成制度（动作路由）

同样是「答得差」，业务上要拆开：

| 现象 | 运营判断 | 该开的工单 | 不该做的 |
|------|----------|------------|----------|
| 高风险问题答不上、知识对不上 | 检索 / 知识库撑不住 | **刷检索 / 换索引 / 补文档** | 一刀切回滚整模 |
| 知识够，但仍胡编、口吻制度变了 | 生成侧制度 hop | **回滚 / 限流 / canary** | 只刷检索假装修好 |
| 差例集中、量不大 | 先止血 | **Top-k 人工审计** | 大动作空转 |

### 3.3 U5 — 审计止血（人力花在刀刃上）

火情期间审计人力有限：不是随机抽，而是先审「最可能出事、审完最值」的会话。  
业务结果：审计件数 × 单价进 **净贡献扣减**；回本表里 `audit_topk` 往往最快回本（日成本低）。

### 3.4 U6 — 文风 / 画风 / 素材漂移（另账）

Feed 文案、广告创意、助手「说话味道」漂了——用户感觉得到，但 **钱路径不是客服工单**，而是 CTR、品牌事故、素材重做。  
硬规则：**永不并进客服主账**，避免用文风信号去误伤对齐头或客服回滚决策。

### 3.5 U7 — 流量外推 + FSDS 指标诊断

两件事叠在一起，别混：

| 问题 | 工具 | 回答 |
|------|------|------|
| 试点费率放到生产值多少钱？ | 同费率 × 日会话 | 月毛¥ 外推 |
| **扩量后哪个指标/特征族先出问题？** | **FSDS** | 定位「谁在漂」→ 开修特征 / 限流 / 换路由工单 |

读法：外推给规模；FSDS 给 **坏点清单**（不是又一个总分）。扩量场景下最怕「整体还行、某一族 KPI 先崩」——FSDS 就是干这个的。

### 3.6 U8–U10 — 还值得单独开的落地 case

| Case | 业务问题 | 动作 |
|------|----------|------|
| **特征库 / Embedding 批次** | 新特征批次、新 embedding 是否跟黄金参考一致 | 几何预检不过 → 拒批次；FSDS 家族 mass → 修哪一族特征 |
| **多模态 / 多塔调度** | 视频·音频·文本哪一塔在漂 | 只刷新漂的那一路（KV / LoRA / 重编码预算），别全塔重算 |
| **合成数据验收** | 合成偏好/问答是否把映射带偏 | 合并前 RFPerm 门禁；不合格隔离 |
| **拒答 / 安全策略 hop** | 安全头工作点是否换了（别把流量画像当成模型变坏） | 策略双跑、限量切流 |
| **Router + RAG 路由** | 哪类问题/哪路专家质量在掉 | 优先刷新该专家或该检索器 |

## 4. 客服助手业务逻辑（不谈算法）

产品面：`shop_assistant`（店铺 / 电商客服助手）。

### 4.1 产品在干什么

用户问物流、尺码、退货、活动规则；助手回答。会话结局只有几类运营在乎的结果：

| 结局 | 含义 |
|------|------|
| **机器人承接** | 没升级人工工单，也没走到退款——助手独立消化掉 |
| **出工单** | 转人工 / 建了客服工单（人力成本） |
| **退款** | 会话链路走到退款（钱直接出去） |
| **审计** | 抽检差例（人力件成本） |

单价（本原型假设，财务可改）：工单 ¥25 · 退款 ¥80 · 成功承接 ¥3.5 · 审计件 ¥6。

### 4.2 故事线（三态，不是「模型好不好」）

```text
平静期                火情期 · 不动作              火情期 · 动作落地
工单低、退款低、        工单/退款飙升、             费率被拉回接近平静
承接接近满负荷     →   承接崩掉（大量转人工）  →   事故被按住
```

本原型费率读法（示意数字，见贡献账）：

| 费率 | 平静 | 火情不动作 | 火情动作后 |
|------|------|------------|------------|
| 工单率 | ~1.5% | ~16% | ~1.1% |
| 退款率 | ~0.6% | ~10.5% | ~1.2% |
| 承接率 | ~98% | ~75% | ~98% |

**业务含义**：火情若不动作，助手大面积失效（转人工 + 退款）；动作不是为了刷 AUROC，是为了把费率拉回可运营区间。

### 4.3 增量怎么定义（对账逻辑）

只在「同一火情对照窗」里比：

- **动作落地的那些天**（acted）  
- **同条件没动作的那些天**（ignored）

增量不是「比上周好」，而是：

```text
少工单   = (不动作工单率 − 动作工单率) × 动作侧会话数
少退款   = (不动作退款率 − 动作退款率) × 动作侧会话数
多承接   = (动作承接率 − 不动作承接率) × 动作侧会话数

毛贡献¥ = 少工单×¥25 + 少退款×¥80 + 多承接×¥3.5
净贡献¥ = 毛贡献¥ − 动作侧审计人力成本
```

读法：

- **少工单 / 少退款** = 止损  
- **多承接** = 自助产能回来了（机器人又顶住量了）  
- 三项单价不同，必须分列，不能并成一个「质量分」

本原型量级（示意）：少工单 ~206 · 少退款 ~130 · 多承接 ~316 → 毛 ~¥1.67 万 · 扣审计净 ~¥1.66 万。

### 4.4 运营开得出的三张工单

| 动作 | 什么时候开 | 业务在干什么 | 日成本进回本分母 |
|------|------------|--------------|------------------|
| `retrieval_refresh` | 像是「答不上 / 知识对不上」 | 刷索引、补知识、修检索 | 检索日成本 |
| `model_rollback` | 像是「生成制度坏了」 | 回滚版本、canary、限流 | 回滚日成本 |
| `audit_topk` | 先止血、人力盯最差会话 | 人工抽检队列 | 队列日成本 + 审计件 |

优先顺序看 **净贡献 / 回本**：本原型里回滚臂贡献最大，审计臂回本最快——经营上可以「大动作止血 + 小成本抽检」并行。

### 4.5 经营层还要看什么（仍不谈算法）

| 视图 | 业务问题 |
|------|----------|
| **周经营 / WoW** | 哪一周火情最重、净贡献是正是负 |
| **周归因** | 这周的毛¥里，工单 / 退款 / 承接各贡献多少（财务对账） |
| **动作净贡献** | 扣掉动作日成本后，哪个动作真正赚钱 |
| **回本天数** | 日成本 / 日均毛，当天能不能回本 |
| **承接进回本** | 仅靠「多自助」这一项，能不能把动作成本赚回来 |
| **覆盖率外推** | 火情日只动了 50%，拉到 75%/100% 还能多拿多少 |
| **单价敏感度** | 财务把工单/退款/承接单价改 ±20%，账还站不站得住 |
| **边际再动一天** | 再动作 1 天期望毛/净多少；桌上还留多少 ignored 留白 |

### 4.6 对外可粘贴的一句（业务）

> 幻觉制度跳变后，客服助手相对同条件不动作：少约 206 工单、130 退款、多承接约 316 次；净贡献约 ¥16,590；优先落地模型回滚，辅以检索刷新与 Top-k 审计。

### 4.7 响应是不是 multinomial？下一步怎么评？delay 的利润差？

**是的——可以（也应该）按 multinomial 来读。** 两层：

| 层 | 类别（互斥读法） | 业务含义 |
|----|------------------|----------|
| **会话结局** \(Y\) | 承接 / 出工单 / 退款 /（工单∩退款） | 一次会话落到哪类运营结果 |
| **下一步动作** \(A\) | 不动作 · 刷检索 · 回滚模型 · Top-k 审计 | 火情后选哪张工单 |

账上用的工单率、退款率、承接率，就是这套 multinomial（或边缘）概率的经营读数；单价把概率差变成 ¥。

> 注：承接定义为「无工单且无退款」，与工单/退款在定义上互斥干净；若原始表允许工单∩退款同时为真，完整 multinomial 用 4 格，增量公式仍用费率差 × 单价（对照会计，不是把一条会话卖三次）。

#### 下一步（动作）怎么评估

火情打开后，对每个候选动作 \(a\) 估一套事后 multinomial 费率 \(\pi(y\mid a)\)，算期望经营值，再扣动作日成本：

```text
V(a) = N_day × Σ_y  π(y|a) · price(y)     # 或用费率差相对「不动作」的增量
Net(a) = V(a) − V(ignore) − cost_day(a)

选 a* = argmax Net(a)
```

本原型三臂直觉（同一火情窗）：

| 动作 \(a\) | 评什么 | 典型读法 |
|------------|--------|----------|
| `retrieval_refresh` | 事后承接是否先回来、退款是否降 | rag 低时优先 |
| `model_rollback` | 工单/退款是否整体拉回 quiet | 生成制度 hop 时优先 |
| `audit_topk` | 抽检成本低、止血快 | Net 里成本小，回本最快 |
| ignore | 基准 \(V(ignore)\) | delay 越长，越长时间停在这档 |

**评估下一步 = 比 Net(a)，不是比 AUROC。** 路由信号（检索弱 / 生成 hop / 只想止血）只决定候选集，最终仍用 multinomial 费率 × 单价对账。

#### Detection delay → profit difference

定义：`delay = first_fire_time − true_cut_time`（batch 或天）。

延迟段里系统仍按 **不动作** multinomial 费率跑；若零延迟，这段本可按 **动作后** 费率跑：

```text
ΔProfit(delay) ≈ delay × N_day × Σ_y [ π(y|ignore) − π(y|acted) ] · price(y)
               ≈ delay ×（每动作日毛贡献¥）

ΔNet(delay)    ≈ delay ×（每动作日净贡献¥）
```

本原型量级（贡献账边际日）：

| delay（天 / 等价动作日） | 少拿毛≈ | 少拿净≈ |
|--------------------------|---------|---------|
| **0**（本跑 Halu/HH） | **¥0** | **¥0** |
| 1 | ¥2,379 | ¥2,370 |
| 2 | ¥4,758 | ¥4,740 |
| 3 | ¥7,137 | ¥7,110 |

单会话尺度：ignore→acted 期望经营差约 **¥11.9 / 会话**（工单¥25、退款¥80、承接¥3.5、本原型费率）。  
`delay × 日会话 × ¥11.9` 与上表同阶。

**读法：**

- delay=0 ⇒ 检测本身不额外吃利润；利润差来自「动没动」，不是「晚没晚」。  
- delay>0 ⇒ 每多晚一天，大约少拿 **一个动作日** 的增量（~¥2.4k 毛）。  
- 和「覆盖率留白」同一逻辑：ignored 日 = 自愿/被迫 delay；detection delay = 还没开火就被迫 ignore。

```text
总可归因损失 ≈ ΔProfit(detection_delay) + ΔProfit(已知火情仍 ignored 的天)
```

## 5. 边界（避免 overlaps）

| 要 | 不要 |
|----|------|
| 讲工单 / 退款 / 承接 / ¥ | 用 AUROC / P@10 冒充贡献 |
| 推理流用在线火情；对齐用合并门禁 | 把对齐信号写进客服主账 |
| 文风漂移另开素材账 | 文风一漂就回滚客服模型 |
| 有 acted vs ignored 才报增量¥ | 没有对照臂就报「AI 创造了 XX 万」 |
| PO-risk 只决定「先审谁」 | 把排序器当成事实核查器 |
